PsGameTranslator — Teknik Rehber

Kaynak Kullanımını Düşürme: CPU, RAM, GPU, VRAM

Bu doküman uygulanmadı — sadece yöntemleri ve gerekçelerini anlatıyor. Her teknik gerçek dosya yollarına ve şu anki koda referans veriyor, böylece istediğinde adım adım kendin uygulayabilirsin. GPU & VRAM

GPU · VRAM

Şu anda iki ayrı Python süreci (çeviri sunucusu + OCR sunucusu) aynı GPU'yu paylaşıyor, ikisi de kendi CUDA bağlamını açıyor. En büyük kazanım burada.

1. OPUS-MT'yi CTranslate2 formatına dönüştür

Etki: YüksekZorluk: Orta

Şu an model transformers/PyTorch üzerinden çalışıyor — genel amaçlı bir çalışma zamanı, MarianMT mimarisine özel optimize edilmemiş. CTranslate2, Helsinki-NLP/OPUS-MT ailesini (senin fine-tune ettiğin model dahil) native olarak destekliyor; int8 quantization ile hem VRAM hem de üretim (generate) süresini belirgin şekilde düşürüyor. Bu, PyTorch'un kendi fp16'sından bağımsız, ayrı bir kazanım katmanı.

tools/translation/translation_server.py
# 1) Modeli bir kere dönüştür (kurulum anında, çalışma zamanında değil)
# pip install ctranslate2
ct2-transformers-converter \
    --model "PsGameTranslator.App/bin/Debug/net8.0-windows10.0.19041.0/models/opus-mt-finetuned" \
    --output_dir "models/opus-mt-finetuned-ct2" \
    --quantization int8_float16   # GPU için: ağırlıklar int8, aktivasyonlar fp16

# 2) Sunucuda yükleme ve çeviri (transformers yerine)
import ctranslate2
import sentencepiece as spm

translator = ctranslate2.Translator("models/opus-mt-finetuned-ct2", device="cuda")
sp_source = spm.SentencePieceProcessor(model_file=".../source.spm")
sp_target = spm.SentencePieceProcessor(model_file=".../target.spm")

def translate_ct2(text: str) -> str:
    tokens = sp_source.encode(text, out_type=str)
    result = translator.translate_batch([tokens], beam_size=1)
    return sp_target.decode(result[0].hypotheses[0])
Şimdi (fp16, PyTorch)
~460 MB model + ~700 MB sabit CUDA yükü
CTranslate2 int8
~130-180 MB model, benzer sabit yük

Risk: int8 quantization çok nadiren 1-2 BLEU puanı kaybettirebilir — fine-tune sonrası aldığın BLEU 34.4 gibi bir referans skorun varsa dönüştürmeden sonra tekrar ölçüp karşılaştır.

8. Çeviri önbelleğine üst sınır ve LRU tahliye

Etki: Orta (uzun oturumlarda yüksek)Zorluk: Düşük

translation_cache.json şu an 3700+ kayıt taşıyor ve sınırsız büyüyor — her uzun oynanış oturumu dosyayı ve bellekteki sözlüğü büyütmeye devam ediyor. Sabit boyutlu bir LRU (en az kullanılanı at) yapısı bunu sınırlar.

PsGameTranslator.Infrastructure/Translation/TranslationCache.cs
private const int MaxEntries = 8000;

public void Set(string key, string value)
{
    if (_cache.Count >= MaxEntries && !_cache.ContainsKey(key))
    {
        var oldest = _accessOrder.First();   // LinkedList ile LRU sırası tutulur
        _cache.Remove(oldest);
        _accessOrder.RemoveFirst();
    }
    _cache[key] = value;
    TouchAccessOrder(key);
}

Pipeline optimizasyonu

Genel

Tek bir aşamayı hızlandırmak yerine aşamalar arasındaki bekleme ve gereksiz işi ortadan kaldırmak — genelde tek bir optimizasyondan daha büyük toplam kazanç verir, çünkü darboğaz tek bir yerde değil, aşamaların birbirini senkron beklemesinde.

11. Aşamaları üretici-tüketici (producer-consumer) modeline taşı

Etki: YüksekZorluk: Orta-Yüksek

Şu anki akış büyük ölçüde sıralı: yakala → kırp → OCR bekle → sınıflandır → çeviri kuyruğuna koy. Bir sonraki karenin yakalanması, mevcut karenin OCR'ı bitene kadar büyük ölçüde bekliyor (loglarda capture_to_ocr_done_ms'un tek bir OCR isteğinden çok daha yüksek çıkması bunun izi). Yakalama, OCR ve çeviriyi ayrı Channel<T> kuyruklarıyla birbirinden ayrık task'lara bölmek, bir aşama meşgulken diğerinin boş beklemesini engeller — GPU OCR ile meşgulken CPU zaten bir sonraki kareyi yakalayıp kırpmış olur.

PsGameTranslator.App/ViewModels/MonitoringViewModel.cs (yeniden yapılanma)
private readonly Channel<CapturedFrame> _captureChannel =
    Channel.CreateBounded<CapturedFrame>(new BoundedChannelOptions(2)
    {
        FullMode = BoundedChannelFullMode.DropOldest,   // bkz. #12 backpressure
    });

// Görev 1: sadece yakala + kırp, sonucu kanala yaz
async Task CaptureLoopAsync(CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        var frame = await CaptureAndCropAsync(ct);
        await _captureChannel.Writer.WriteAsync(frame, ct);
        await Task.Delay(CurrentIntervalMs, ct);
    }
}

// Görev 2: kanaldan oku, OCR + sınıflandırma + çeviri kuyruğu — paralel çalışır
async Task ProcessLoopAsync(CancellationToken ct)
{
    await foreach (var frame in _captureChannel.Reader.ReadAllAsync(ct))
        await RunOcrAndDispatchAsync(frame, ct);
}

// Başlangıçta ikisini de bağımsız başlat:
_ = Task.Run(() => CaptureLoopAsync(ct));
_ = Task.Run(() => ProcessLoopAsync(ct));

12. Backpressure: kuyruk sınırı ve en yeni kareyi tutma

Etki: Yüksek (aşırı yük altında)Zorluk: Düşük

OCR'ı CPU'ya aldığımız denemede tam olarak gördüğümüz şey buydu: OCR süresi kare aralığından uzun sürünce istekler kuyrukta birikti, gecikme 561ms'den 4900ms'ye kadar tırmandı. Sınırsız bir kuyruk, geç kalan sistemi daha da geciktirir çünkü eski, artık alakasız kareleri bile işlemeye devam eder. Sınırlı kapasiteli bir kanal + DropOldest politikası, sistem yetişemediğinde en eski (zaten bayatlamış) kareyi atıp en güncel kareye odaklanır.

Yukarıdaki BoundedChannelOptions(2) — kapasite 2, dolunca en eskisini at
// Sınırsız Queue<T> yerine:
var options = new BoundedChannelOptions(capacity: 2)
{
    FullMode = BoundedChannelFullMode.DropOldest,
    SingleReader = true,
    SingleWriter = true,
};

Bu yaşadığımız gerçek bir olaydı: OCR'ı CPU'ya taşıdığımızda arka arkaya biriken isteklerin gecikmesi katlanarak arttı — backpressure olsaydı sistem "yetişemiyorum" deyip en son kareye atlardı, birikme yerine.

13. Başlangıçta ısınma (warm-up) isteği at

Etki: Orta (ilk istek gecikmesi)Zorluk: Düşük

CUDA'nın ilk çekirdek derlemesi/yükü ("kernel warm-up") ilk isteği belirgin şekilde yavaşlatır — bu oturumda ölçüm yaparken de her seferinde önce görünmez bir "warmup" isteği attık, tam da bu yüzden. Sunucu açılışında gerçek bir çeviri/OCR isteğini sahte bir metinle bir kez tetiklemek, kullanıcının göreceği ilk gerçek altyazının o soğuk-başlangıç gecikmesini yememesini sağlar.

14. Sahne durgunken tarama aralığını uzat

Etki: Yüksek (boşta senaryoda)Zorluk: Orta

Şu an tarama aralığı sabit (~300-400ms), diyalog olsun olmasın. Art arda birkaç kare "değişiklik yok / metin yok" dönerse aralığı kademeli arttırıp (örn. 400ms → 800ms → 1500ms), yeni bir değişiklik algılanınca hemen 400ms'e dönmek — boşta CPU/GPU tüketimini büyük ölçüde azaltır, diyalog başladığında tepki hızını korur.

PsGameTranslator.App/ViewModels/MonitoringViewModel.cs (tarama zamanlayıcısı)
private int _consecutiveEmptyFrames;
private int CurrentIntervalMs =>
    _consecutiveEmptyFrames switch
    {
        <= 2 => 400,
        <= 6 => 800,
        _     => 1500,
    };

// her boş OCR sonucunda: _consecutiveEmptyFrames++;
// her dolu sonuçta:      _consecutiveEmptyFrames = 0;

15. Stabilizasyon süresini içerik uzunluğuna göre uyarlama

Etki: OrtaZorluk: Orta

Şu anki 250ms sabit — kısa repliklerde ("Hayır.") gereksiz beklemeye, uzun diyalog daktilo efektinde bazen yetersiz kalmaya sebep olabilir. Metin uzunluğuna göre orantılı bir bekleme (kısa metne az, uzun metne biraz daha fazla) hem tepki hızını hem doğruluğu iyileştirebilir.

PsGameTranslator.Infrastructure/Translation/OrderedSubtitlePipeline.cs (HandleStabilization)
var stabilizationMs = Math.Clamp(
    150 + text.Length * 2,   // kısa metin ~150-200ms, uzun metin ~350-400ms
    150, 400);

Bu ayarı önceki oturumda bilerek sabit 250ms'de bıraktık (kullanıcı isteğiyle) — burada sadece bir sonraki iyileştirme fikri olarak listeleniyor, otomatik uygulanmadı.

Uygulama sırası

Etki/zorluk oranına göre gerçek bir öncelik sırası — yukarıdan aşağı uygulaman önerilir.

  1. Backpressure / kuyruk sınırı ekle (#12)Riski yok, sadece iyileştirir — OCR-CPU denemesinde yaşadığımız birikme sorununu tekrar yaşamamamızı garantiler.
  2. OCR isteklerini birleştir (#3)Tek kod değişikliği, hemen ölçülebilir round-trip kazancı.
  3. Görüntüyü küçült + JPEG'e geç (#4, #5)İkisi birlikte kırpım→OCR yolunun CPU maliyetini büyük ölçüde düşürür.
  4. Başlangıç ısınma isteği (#13)Beş satırlık kod, ilk çevirinin soğuk-başlangıç gecikmesini yok eder.
  5. Uyarlanabilir tarama aralığı (#14)Boşta senaryoda (menü, ara sahne) en büyük genel kazanım.
  6. Çeviri önbelleğine LRU sınırı (#8)Uzun oturumlarda RAM artışını durdurur, riski yok.
  7. Üretici-tüketici pipeline'a geçiş (#11)En büyük mimari kazanım ama en fazla test gerektiren refactor.
  8. CTranslate2'ye geçiş (#1)En yüksek etki ama BLEU'yu tekrar ölçmeyi gerektirir — ayrı bir oturumda ele alınmalı.
  9. OCR + çeviriyi tek sürece birleştir (#2)En büyük VRAM kazancı ama en riskli refactor — en sona bırakılmalı.
